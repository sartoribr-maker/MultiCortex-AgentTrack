1. O QUE É
----------
O DevCore Monitor é o painel interno da MultiCortex para acompanhar as POCs (provas de
conceito) do DevCore. O DevCore é um servidor de LLM (llama.cpp, modelo "DEVCORE-Good",
API compatível com OpenAI em /v1) usado por desenvolvedores de clientes nas suas IDEs.
O painel mostra, por VM/POC: requisições, erros, tempos de resposta, espera até o primeiro
token, uso de GPU/VRAM, ocupação dos slots do llama.cpp, desenvolvedores ativos (por IP)
e um parecer técnico automático com recomendações.

No pod (só saída de rede, modo "push"):
  - devcore_http_capture.py: o tcpdump entrega uma CÓPIA passiva dos pacotes da porta 7080.
    A captura lê só os cabeçalhos HTTP e grava /var/log/devcore-poc/requests-AAAAMMDD.log

  - devcore_metrics_agent.py, a cada 1 min: agrega logs e amostras em horário de Brasília,
    grava /srv/www/devcore-metrics/metrics.json e envia por POST para .../ingest/<vm>.
  - O histórico de dias fechados fica em /var/lib/devcore-metrics/state.json (até 45 dias).

3. RESTRIÇÕES QUE NÃO PODEM SER VIOLADAS
----------------------------------------
- Não propor mudanças no DNS de devcore01.multicortex.com.br, nas portas do gateway Apache
  35.168.36.211 nem no llama.cpp. Por isso as medições são passivas (tcpdump).
- Contrato com o agente (não pode mudar):
  - endpoints POST /api/devcore/ingest/<id> e /api/devcore/ingest/<id>/live;
  - Bearer token comparado em tempo constante;
  - 401 IGUAL para VM inexistente e para token errado;
  - corpo limitado a 2 MB (413 acima disso), JSON inválido = 400, schema inválido = 422, sucesso = 204;
  - schema em src/lib/devcore/metrics-schema.ts, compatível com os agentes 1.0 a 1.4;
  - tests/fixtures/devcore-metrics.sample.json é o contrato e precisa continuar passando.
- Segurança e privacidade:
  - tokens só no servidor, nunca no navegador nem nos logs;
  - a captura nunca grava corpos de requisição;
  - o IP de cada desenvolvedor é dado pessoal (LGPD) e só aparece com login.
- Uma única instância do app, porque os dados ficam em memória.
- Nada pode ser indexado: X-Robots-Tag "noindex, nofollow, noarchive" em todas as respostas,
  meta robots no layout e robots.txt com Disallow: /.

6. REGRAS DOS INDICADORES (resumo; horário de Brasília, UTC-3 fixo)
--------------------------------------------------------------------
- Requisições: POST /v1/chat/completions do host DevCore (devcore_hosts do agent.conf).
- Taxa de erro: (4xx + 5xx) / requisições. O 499 (cliente cancelou o streaming) fica fora
  da taxa e aparece à parte como "canceladas".
- Tempo de resposta (rt): do primeiro byte da requisição até o fim da resposta.
- Espera até o modelo responder (uht): até o primeiro byte do corpo da resposta, isto é, o
  primeiro token no streaming. Mediana e p95, só de respostas 2xx. Sem streaming, uht = rt.
- Desenvolvedores ativos: IPs distintos (do X-Forwarded-For) com ao menos uma chamada /v1/*
  2xx no dia. Localhost fica de fora. Vários devs atrás do mesmo NAT contam como um IP.
- Lista por desenvolvedor (só com login): requisições, erros, primeira e última chamada,
  tempo ativo (união dos intervalos, juntando chamadas com até 5 min de intervalo), medianas.
- Card "Agora": devs on-line (requisição em andamento ou 2xx nos últimos 5 min), slots em
  uso contra os slots da VM (o excedente está na fila), GPU agora. Vale 30 s; depois disso
  o card mostra "Parado".
- Requisições simultâneas: segundo a segundo, cada POST ocupa um slot de (ts - rt) até ts.
- Status do painel: "Atrasado" quando generated_at tem mais de 5 min; "Indisponível" sem envio há mais de 15 min.
- Parecer técnico, limites:
  - contexto recusado >= 5% das requisições = atenção;
  - espera p95 >= 10 s = observar; >= 30 s = atenção;
  - geração < 20 tokens/s = observar; < 10 = atenção;
  - slots esgotados > 0% = observar; >= 10% = atenção;
  - VRAM >= 90% = observar; >= 97% = atenção;
  - 5xx >= 1% = atenção.
  - Sem o bloco today.server (journal do llama.cpp), o parecer é PARCIAL. No pod não há
    journal (server_unit vazio), então hoje o parecer é sempre parcial.


7. LOGIN (próprio, sem banco)
-----------------------------
- Auth.js (Credentials + JWT) contra a variável DEVCORE_USERS.
- Formato: "email:hash[:Nome]", com várias entradas separadas por vírgula. O hash é bcrypt
  em base64 (para evitar "$" no arquivo .env); um hash $2b$ cru também é aceito.
- Para gerar uma entrada: npm run hash-password -- email@dominio "Nome".
- Para gravar direto no servidor, sem copiar e colar (padrão que funcionou com o usuário):
    npm run -s hash-password -- EMAIL "NOME" | ssh ec2-user@52.207.145.100 'read -r E; case "$E" in EMAIL:*) ;; *) echo ERRO >&2; exit 1;; esac; F=/opt/multicortex/devcore-monitor/.env.production; sudo sed -i "/^DEVCORE_USERS=/d" "$F"; printf "DEVCORE_USERS=%s\n" "$E" | sudo tee -a "$F" >/dev/null; echo gravado'
  ATENÇÃO: esse comando SUBSTITUI a lista inteira. Para incluir uma pessoa, é preciso
  acrescentar a nova entrada às atuais, separada por vírgula.
  Depois de alterar, recrie o contêiner para valer.
- Hoje existe 1 usuário: tiago.sartori@multicortex.ai ("Tiago Sartori").
- Regras de acesso: anônimo vai para /entrar. Sessão de e-mail removido da lista = acesso
  negado ("Sua conta não tem perfil de equipe MultiCortex."). Logout volta para /entrar.
- Cookie __Secure-authjs.session-token, HttpOnly, só do host devcore.multicortex.com.br.
- AUTH_SECRET é próprio do painel, diferente do site.
